# Домашнее задание к занятию «13. Системы мониторинга»

## Задание 1.

1.**CPU (Утилизация и Load Average):** Платформа выполняет ресурсоемкие вычисления, важно отслеживать очереди задач к процессору и общую загрузку ядер.
2.**RAM (Использование и доступная память):** Нехватка оперативной памяти может привести к использованию swap, что критически замедлит вычисления, или к аварийному завершению (OOM Killer).
3.**Disk (IOPS, Throughput, Free Space, Inodes):** Сохранение текстовых отчетов генерирует операции ввода-вывода и расходует место. Метрика Inodes (индексные дескрипторы) обязательна, так как создание большого количества мелких текстовых файлов может исчерпать лимит дескрипторов до исчерпания дискового пространства.
4.**HTTP/Network (Количество запросов, время ответа, коды статусов):** Для контроля доступности платформы для пользователей (RED-метрики: Rate, Errors, Duration).

## Задание 2.

1. **SLI (Service Level Indicator):** Текущие показатели работы платформы. Например, процент успешных HTTP-ответов (не 5xx) и время ответа на запрос (latency).
2. **SLO (Service Level Objective):** Целевые значения для SLI. Например, «99% отчетов должны генерироваться быстрее, чем за 5 секунд», «Доступность сервиса 99.9% в месяц».
3. **Error Budget** (Бюджет на ошибки): Допустимое количество отказов за период, при исчерпании которого останавливается выкатка новых фич и команда фокусируется на стабильности.
Для наглядности менеджеру нужно настроить дашборд с RED-метриками (Количество запросов, Количество ошибок, Время выполнения запросов), абстрагировав его от загрузки CPU и дисков.

## Задание 4.

Формула summ_2xx_requests/summ_all_requests не учитывает информационные (1xx) и коды перенаправлений (3xx).
Редиректы (например, 301, 302, 304 Not Modified) являются штатным поведением сервиса и не свидетельствуют о деградации SLA. Если доля 3xx ответов составляет 30%, формула покажет SLA 70% даже при полном отсутствии реальных ошибок (4xx и 5xx).
Правильная формула: (summ_all_requests - summ_5xx_requests) / summ_all_requests (или исключить 1xx/3xx из знаменателя, если SLA считается только по 2xx).

## Задание 5.

|**Pull** (сервер сам опрашивает агентов, например, Prometheus):|
|**Плюсы:** Единая точка конфигурации на сервере; легко обнаружить падение узла (сервер знает, кого опрашивать); защита от DDoS (сервер контролирует частоту опросов) |
|**Минусы:** Проблемы с опросом нод за NAT или firewall (требуются прокси); сложно мониторить короткоживущие процессы (cron-задачи могут завершиться до момента опроса) |
|**Push** (агенты сами отправляют данные на сервер, например, TICK, Zabbix-trapper): |
|**Плюсы:** Идеально для машин за NAT; легко мониторить короткоживущие задачи/скрипты; агенты можно динамически добавлять без перенастройки сервера |
|**Минусы:** При масштабировании множество агентов может перегрузить центральный сервер; падение агента сложнее диагностировать (данные просто перестают поступать) |

## Задание 6.

|**Prometheus:** Pull-модель (имеет Pushgateway для короткоживущих метрик) |
|**TICK (Telegraf, InfluxDB):** Push-модель |
|**Zabbix:** Гибридная (Active checks — Push, Passive checks — Pull) |
|**VictoriaMetrics:** Гибридная (опрашивает pull-таргеты, принимает push-данные в различных форматах) |
|**Nagios:** Pull (базовая проверка портов, NRPE) и Push (через NSCA) |
